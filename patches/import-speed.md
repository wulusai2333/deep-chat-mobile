# 导入历史会话提速（0.2.5）

> 对应改动：`web-patches/import-bridge.ts`、`web-patches/mobile/overrides/history/zipReader.ts`、
> `web-patches/native-backup.ts`、`scripts/prepare-web.mjs` 里的 `db.ts` / `store.ts` / `backup.ts` /
> `SettingsDialog.tsx` 补丁，以及 `native/file-open/FileOpenPlugin.java` 的分块常量。
> 测量环境与 0.2.4 相同：真实归档 31.3 MB / 677 条目 / 593 条会话 / 81 张图，桌面无头 Chrome。

## 1. 用户反馈与现象

真机上导入 600 多条会话：前面的「校验」等很久；随后进度大约「一秒一条」，整包要分钟级。
桌面上同一份归档只要 3.2 s（空库）。差两个数量级，说明不是单纯的 CPU 慢，而是有几处
**随条目数放大**的固定成本，被手机上的存储/IO/定时器放大。

## 2. 定位到的五个成本点

| # | 成本点 | 为什么在手机上被放大 |
| --- | --- | --- |
| A | `checkArchiveFormat()` 解析整份中央目录：每个条目 3~4 次 `file.slice().arrayBuffer()`（677 条目 ≈ 2000+ 次） | WebView 每次 slice 都要过一次浏览器进程/文件读取，桌面 444 ms、真机数秒 |
| B | 每条会话被切成 8 KB 小块、每块 `new Blob`、再拼合 `.text()` | Blob 创建/读取在 WebView 里是跨进程对象，逐条累加很贵 |
| C | 合并导入把**本机全部数据**复制进暂存，结束时再整表搬回（并集方案） | 一次导入写 2~3 倍数据；本机 600 条时是纯浪费 |
| D | 重复导入：账本指纹在 `JSON.parse + toLocalSession` **之后**才命中 | 已导入过的会话仍付全价 |
| E | 备份在前、解析在后；而且备份前不会判断「数据到底变没变」 | 每次导入都先读 600 条会话、生成 50 MB ZIP、200 次过桥写盘，哪怕这次一条都导不进去 |
| F | 对 `content://` 来的 File 反复 `slice().arrayBuffer()` | Android 上每次 slice 都重新 open + seek 到偏移：几十次小块读退化成 O(n²) provider 读取。**真机第二轮实测：32 MB 归档光「跳过已导入」就要 36 s** |

## 3. 改动

### 3.1 `zipReader.ts` 升级为整文件 fork（`web-patches/mobile/overrides/history/`）

- 中央目录**一次读完**，在内存里同步解析：2000+ 次小块读变成 1 次（校验阶段 444 ms → 14 ms）。
- 每条目「本地头 + 文件名」一次读完，`extra` 非空时才再读。
- 新增 `readEntryBytes()`：会话 JSON 直接拿字节 `TextDecoder` 解码，不再造一串 8 KB Blob。
- `ArchiveEntry` 暴露 `crc` 与 `discard()`：前者给账本做「内容指纹」，后者让已确认导入过的条目
  **不 inflate、不校验 CRC** 直接跳过（只读掉压缩字节）。
- 目录上限 8 MB 防御构造归档；其余校验规则、错误类型与上游一致。

### 3.2 合并导入主流程（`import-bridge.ts`）

- **先把归档一次性读进内存**（≤ 48 MB）：`materializeArchive()` 只 `arrayBuffer()` 一次，
  之后所有 `slice` 都在内存 Blob 上。这是真机上最大的一处提速（见 §4 的真机表）。
- **顺序改为**：格式校验 → 读摘要（得到 `existing` + 备份指纹）→ 解析并写暂存 → 判断是否需要备份 → 增量提交 → 写账本。
- **账本 v2**：键 `会话id|CRC|解压后大小`，三者都来自已校验的中央目录。
  命中且本机仍存在该会话 → `discard()`，不解析、不写库。旧版文本指纹键自动淘汰（升级后多解析一轮）。
- **备份按需**：本机没有会话 / 本次没有任何新增更新 / 上次成功后数据没变（摘要条数 + 最新 updatedAt + 标题指纹）
  / 用户在确认弹窗取消勾选 —— 任一成立就跳过备份。备份仍然严格发生在写正式表之前。
- 进度：阶段、`已处理/总数`、`已跳过（导入过）`；解析完/备份/提交分别报阶段。
- 屏幕常亮：`navigator.wakeLock`（失败静默）。页面不可见时 `setTimeout` 会被钳制到约 1 秒，
  所以让出主线程改用 `MessageChannel` 宏任务（`native-backup.ts` 的 `yieldToPaint`）。

### 3.3 落库（`db.ts` / `store.ts` 补丁）

- 新增 `commitMergeStaging()`：单事务把暂存里的「本次导入」`put` 进正式表并清空暂存，
  **不清空正式表**。原子性与上游 `commitStaging` 一致（失败 abort 回滚），写入量降到 1/3。
- `replaceHistory(write, commit = db.commitStaging)` 增加可选提交函数；上游所有调用点不传，行为不变。
- 删除 `stageCurrentHistory()`（不再需要并集）。
- 新增 `loadSessionsBatch()` / `loadFilesBatch()`：备份导出按 25 条一批读，600 个只读事务 → 约 24 个。

### 3.4 桥与 UI

- 分块上限 256 KB → 1 MB（`native-backup.ts` + `FileOpenPlugin.MAX_CHUNK_BYTES`），过桥往返少 4 倍。
- 进度浮层关掉全屏 `backdrop-filter`（真机上每帧重新合成整屏），更新限频到约 12 Hz，去掉宽度过渡。
- 结果页增加耗时明细（校验/解析/备份/写入）与「其中 N 条已导入过，未重新解析」。
- 导入确认弹窗在原生壳里改为「合并」说明，并提供「导入前自动备份本机数据」复选框（默认开）。

## 4. 桌面实测（同一归档）

| 指标 | 0.2.4 | 0.2.5 | 变化 |
| --- | --- | --- | --- |
| 格式校验 | 444 ms | **14 ms** | −97% |
| 空库导入 593 条 | 3218 / 3255 ms | 3206 / 3244 ms | 基本持平（解析/写库占大头） |
| 已有 593 条时重复导入（全部已导入过） | 7967 / 8205 ms | **917 / 950 ms** | **−89%** |
| 重复导入时实际解压解析的会话数 | 593 | **0** | 全部走账本快速跳过 |
| 峰值 JS heap | 85.2–102.6 MB | **73.6 MB** | −14% ~ −28% |
| 81 张图片入库 | 81 | 81 | 不变 |

说明：空库导入在桌面上没有明显变快，因为它的耗时主要花在「解压 + JSON.parse + 严格校验 +
树重建」，这部分没有被削掉（真机上 I/O 和逐条写库占比更高，收益会比桌面大）。
重复导入是用户最常遇到的场景（导过一次再导、换机后补导），这里从 8.2 s 降到 0.95 s。

### 真机实测（HONOR BVL-AN16 / HarmonyOS 4.3 / API 32，同一 32.8 MB 归档）

阶段耗时来自应用自己的 `[import-perf]` 日志（`adb logcat -s Capacitor/Console`）：

| 场景 | 0.2.5（未一次性读入） | 0.2.5（最终） | 说明 |
| --- | --- | --- | --- |
| 空库首次导入 593 条 | 42.9 s（校验 157 ms + 解析 41.5 s + 写入 1.2 s） | **4.1 s**（读取 126 ms + 校验 27 ms + 解析 2.9 s + 写入 1.2 s） | 首次导入的真正成本在解压/解析/写库 |
| 已有 593 条时重复导入 | 36.3 s（解析 36.1 s，593 条全部快速跳过） | **1.6 s**（读取 112 ms + 校验 41 ms + 解析 1.5 s + 写入 0.14 s） | 账本命中后不 inflate、不 parse、不写库 |

第二轮导入 36 s 全部花在「跳过」上，是定位到 content:// 随机读退化后的关键证据：
先把文件一次性读进内存后，同样的「跳过」从 36 s 降到 1.5 s（读取 112 ms）。
两轮合计耗时从约 79 s 降到约 5.7 s。

真实设备、真实归档、release 同款代码路径（隔离包名 + 清空数据后测量）。

## 5. 不变量（改动不能破坏的东西）

- **原子性**：导入仍是一个事务；失败时暂存清空、正式数据不变（`test:import` 场景 18 断言）。
- **幂等**：同一个 ZIP 连导三次，会话数不变（场景 1–3）。
- **合并语义**：同 id 取较新的 `updatedAt`，本机较新时绝不被覆盖（场景 4–5）。
- **跨端**：ZIP 仍是 v3 结构，手机导出的包能被桌面 chat-demo 读取（场景 10b）。
- **单条坏会话**只记 `failed`，ZIP 结构损坏才整批回滚（场景 8–9）。
- **浏览器/PWA**：`isNativeShell()` 为 false，不走合并导入与备份，桌面行为不变。

## 6. 已知限制

- 空库首次导入仍是「写暂存 + 搬入正式表」两次写，写入量没有降到 1 次（换取原子性）。
- 一次性读入内存的代价是峰值多一份归档大小（≤ 48 MB）；超过 48 MB 的归档回退为原生分块读取路径。
- 账本命中后跳过 CRC 校验（`discard()`）；只影响「这条本来就不导入」的情形，正式数据仍逐条校验。
- 备份 ZIP 仍是全内存 STORE 格式；本机数据特别大时峰值与耗时仍随数据量增长。
- 真机数字以 `[import-perf]` 日志为准（`adb logcat -s Capacitor/Console`），桌面数字不等价于手机。
